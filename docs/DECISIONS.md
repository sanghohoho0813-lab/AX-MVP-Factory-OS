# DECISIONS — MIRAE AI LAB OS × Customer Platform

기록 형식: DECISION / WHY / WHY NOT ALTERNATIVE / REVISIT WHEN. 중요한 결정만 남긴다.

---

## D-01 두 저장소를 유지한다 (monorepo 전환 안 함)

- **DECISION** 내부 OS(`AX-MVP-Factory-OS`)와 고객 플랫폼(`mirae-ai-lab-homepage`)을 별도 저장소로 두고, 같은 Supabase project 의 명시적 계약(RPC·테이블)으로만 연결한다.
- **WHY** 두 앱은 배포 주기·보안 경계·빌드 도구(Vite 8 vs Vite 6)·공개 범위가 다르다. 공개 사이트의 SEO·결제·도구 접근 통제는 지금 그대로 살아 있어야 한다.
- **WHY NOT** monorepo 는 공유 코드가 생기면 좋지만, 지금 공유되는 것은 "타입 몇 개와 단계 이름"뿐이다. 그 정도는 문서(CUSTOMER_DATA_CONTRACT)와 SQL 이 SSOT 가 되는 편이 안전하다.
- **REVISIT WHEN** 세 번째 표면(파트너/기관 포털)이 생기거나, 두 앱이 같은 컴포넌트 라이브러리를 쓰기 시작할 때.

## D-02 새 Supabase project 를 만들지 않고 같은 DB 안에 명시적 브릿지를 둔다

- **DECISION** `portal_client_links` · `customer_events` · `portal_updates` · `portal_requests` · `portal_documents` 로만 왕복한다. DB-to-DB 동기화 없음.
- **WHY** 고객 계정(profiles)·주문·진단 리드가 이미 이 project 에 있다. 동기화를 만들면 두 곳의 진실이 어긋나는 순간 고객에게 잘못된 상태가 보인다.
- **WHY NOT** 별도 project + webhook 동기화는 장애 지점이 하나 더 생기고, RLS 를 두 번 검증해야 한다.
- **REVISIT WHEN** 고객 데이터를 법적으로 분리 보관해야 하는 요구가 생길 때.

## D-03 고객은 내부 payload 를 절대 직접 읽지 않는다 (allowlist RPC 만)

- **DECISION** 고객용 정책을 기본 테이블에 두지 않는다. `portal_*` SECURITY DEFINER 함수가 컬럼을 골라 준 투영만 고객에게 간다. 내부 미리보기(`portal_preview_project`)도 같은 함수를 쓴다.
- **WHY** `operations_clients.payload` 에는 메모·수임료·미수금·자금 판단이 있다. RLS 는 행을 막지 컬럼을 막지 못한다.
- **WHY NOT** 컬럼 권한(GRANT SELECT (col))은 PostgREST 임베드와 섞이면 실수하기 쉽고, 뷰는 RLS 우회가 잦다.
- **REVISIT WHEN** 고객에게 보여줄 필드가 늘어 함수 하나가 너무 커질 때 — 그때도 "함수 = allowlist" 원칙은 유지.

## D-04 사용자 노출 브랜드만 바꾸고 저장소·Vercel·도메인은 바꾸지 않는다

- **DECISION** 화면·문서·파비콘·제목은 MIRAE AI LAB OS. GitHub 저장소명, Vercel project(`ax-mvp-factory-os`), Production URL 은 그대로.
- **WHY** 인프라 이름 변경은 배포 파이프라인·환경변수·북마크를 한꺼번에 깨뜨릴 수 있고 사용자에게 보이지도 않는다.
- **WHY NOT** 전부 rename 하면 깔끔하지만 이번 단계의 목적(매일 쓰는 제품)과 무관한 위험이다.
- **REVISIT WHEN** 별도 도메인(예: os.miraeailab.com)을 붙일 때 — 그때 Vercel project 는 그대로 두고 도메인만 추가.

## D-05 브랜드 문자열은 brand.config 한 곳에만 둔다

- **DECISION** `src/brand/brand.config.ts` 가 이름·로고·고객 플랫폼 URL·기본 테마의 SSOT. 컴포넌트는 "미래AI랩"을 직접 쓰지 않는다.
- **WHY** 같은 소스를 다른 컨설팅 SaaS 로 옮길 때 첫 번째로 바꿀 파일이 하나여야 한다.
- **REVISIT WHEN** 다국어가 필요할 때 — 그때는 config 가 locale 별 값을 갖는다.

## D-06 고객 채팅을 만들지 않는다

- **DECISION** 고객→내부는 구조화 요청(`portal_requests` 6종), 내부→고객은 명시 발행(`portal_updates`)만. 실시간 채팅 없음.
- **WHY** 채팅은 "확인해야 할 것"을 다시 대화 속에 묻어 버린다 — 이 프로젝트의 제약(흩어진 정보 조합 비용)을 도로 만든다. 구조화 요청은 이벤트함에 종류·상태와 함께 들어와 놓치지 않는다.
- **WHY NOT** 채팅이 편해 보이지만 대표 1인이 실시간 응대 SLA 를 감당할 수 없다.
- **REVISIT WHEN** 담당자가 2명 이상이고 응대 시간대가 정해질 때.

## D-07 workspace_id 를 모든 신규 내부 테이블의 tenant 경계로 유지한다

- **DECISION** 1인 사용이라도 `workspace_id not null` + `is_workspace_member/can_write_workspace` RLS 를 모든 신규 테이블에 건다. 고객 쪽은 `portal_client_link` 가 별도 경계.
- **WHY** 나중에 SaaS 로 옮길 때 "owner check 생략" 코드를 찾아 고치는 일이 가장 위험하고 지루하다.
- **REVISIT WHEN** 없음 — 원칙.

## D-08 업무 일기는 owner 본인만 읽는다 (같은 워크스페이스 멤버도 못 봄)

- **DECISION** `ops_journal_entries` RLS = `owner_id = auth.uid() and is_workspace_member(workspace_id)`.
- **WHY** 일기에는 "왜 그렇게 판단했는지", 고객에 대한 솔직한 메모가 들어간다. 팀 공유는 명시적 기능으로 따로 만들어야 한다.
- **REVISIT WHEN** Team Journal 요구 — 그때 `visibility` 컬럼을 추가하고 정책을 덧붙인다(additive).

## D-09 고객 공개는 자동이 아니라 "명시 발행"이다

- **DECISION** 내부 업무 상태·활동 기록·메모는 고객에게 자동 전송되지 않는다. `PublishUpdateModal` 에서 쓴 제목·내용·조치·단계만 `published` 가 된다. 고객 단계(6종)도 사람이 고른다(내부 상태로 추천만).
- **WHY** 내부 8단계 중에는 고객이 오해할 단계(대기·보류)가 있고, 활동 기록에는 "입금 확인 500만원" 같은 내부 문장이 있다.
- **WHY NOT** 자동 동기화는 편하지만 한 번의 실수가 신뢰를 깎는다.
- **REVISIT WHEN** 특정 이벤트(예: 기관 접수 완료)를 자동 공개해도 안전하다는 합의가 생길 때 — 그때도 템플릿 발행 형태로.

## D-10 자동 연결은 "후보 제안"까지만

- **DECISION** 이메일·전화·사업자번호가 같아도 `portal_client_links` 를 자동 생성하지 않는다. 이벤트 트리거는 `profile_id` 를 찾아 붙이고, 활성 연결이 정확히 1개일 때만 이벤트에 link 를 붙인다(2개 이상이면 사람이 고른다). 고객사 연결은 `LinkCustomerModal` 에서 사람이 확정한다.
- **WHY** 동명 회사·대표 개인 이메일 공유 같은 경우 잘못 연결되면 남의 프로젝트가 보인다.
- **REVISIT WHEN** 없음.

## D-11 브릿지가 적용되지 않은 환경은 READY 로 표시한다

- **DECISION** supabase 모드에서 브릿지 테이블/함수가 없으면 화면은 "준비 중(READY)" 안내를 내고 나머지 기능은 그대로 동작한다. LIVE 라고 표시하지 않는다.
- **WHY** Claude 실행 환경에서 Production Supabase 에 apply 할 수 없었다(CLI·자격증명 없음). 미적용 상태를 숨기면 Demo 를 Live 로 위장하는 것이다.
- **REVISIT WHEN** SETUP.md 절차로 마이그레이션을 적용한 뒤 — PROJECT_STATE 의 상태를 LIVE 로 바꾼다.

## D-12 하루 정리·Top 3 는 규칙 기반이며 AI 라고 부르지 않는다

- **DECISION** `dailyBriefService` 의 점수와 이유 문장은 코드에 적힌 규칙이다. LLM 은 Adapter 자리만 남긴다(NEXT).
- **WHY** 마감·미수금·주문은 IF 로 충분하다. 설명 가능해야 대표가 순서를 믿는다.
- **REVISIT WHEN** 자연어 정리(예: 통화 메모 요약)에 실제 가치가 확인될 때.

## D-13 첫 화면(/)은 Command Center, /today 는 리다이렉트

- **DECISION** `/` 가 "오늘"이 되고, 기존 `/today` 는 `/` 로 보낸다(구 화면은 `/today/legacy` 로 보존).
- **WHY** 앱을 켠 뒤 5초 안에 오늘 할 일을 알아야 한다. 리다이렉트로 시작하는 홈은 그 질문에 답하지 않았다.
- **REVISIT WHEN** 없음.

## D-14 사이드바 색은 테마와 분리된 고정 분류색이다

- **DECISION** 메뉴 아이콘·분류 배지 색은 `--color-nav-*` / `--color-cat-*` 고정 토큰. 화면 테마(9종)는 shell·primary·accent 만 바꾼다.
- **WHY** "지원사업은 초록, 서류는 노랑" 같은 인지 방식이 테마를 바꿀 때 흔들리면 안 된다. 반대로 일반 강조·버튼·선택 상태는 테마 색이어야 브랜드가 한 몸으로 보인다.
- **REVISIT WHEN** 없음.

## D-15 SaaS 분리는 "복붙"이 아니라 portable core 재사용으로 설계한다

- **DECISION** brand.config · serviceCatalog · moduleRegistry · workspace 경계 · 브릿지 어댑터를 교체 지점으로 두고, SAAS_EXTRACTION_PLAN.md 에 단계별 절차를 남긴다. 이번 단계에서 실제 분리는 하지 않는다.
- **WHY** 파일 복사는 두 코드베이스가 즉시 갈라져 버그를 두 번 고치게 만든다.
- **REVISIT WHEN** 두 번째 고객사(다른 컨설팅 법인)가 확정될 때.

## D-16 기본은 main 직행 배포다. Preview 는 요청이 있을 때만 만든다

- **DECISION** 대표가 요청한 변경은 검증(빌드·린트·테스트·모바일 여정)을 통과하면 곧바로
  `main` 에 병합해 실제 주소(https://ax-mvp-factory-os.vercel.app)에 반영한다.
  "미리 보고 싶다 / 다른 데 먼저 올려서 URL 달라" 는 말이 있을 때만 별도 브랜치 + Vercel Preview 를 만든다.
- **WHY** 대표가 매일 쓰는 주소는 하나뿐이다. 고친 것이 그 주소에 바로 없으면 고친 의미가 없다.
  Preview 는 환경변수가 따로 붙지 않아 로컬 데모 모드(빈 화면)로 뜨는 일이 잦아, 기본 경로로 쓰면
  "데이터가 사라졌다" 는 오해만 만든다.
- **REVISIT WHEN** 여러 명이 동시에 이 저장소를 고치게 될 때 (그때는 PR 검토가 필요하다).

## D-17 처음 사용 가이드는 저절로 뜨지 않는다

- **DECISION** 접속할 때 자동으로 안내창을 띄우지 않는다. '처음 사용 가이드' 버튼을 눌렀을 때만 연다.
  자동 노출 판단 로직과 설정 스위치도 함께 제거했다(가이드 내용 자체는 그대로 유지).
- **WHY** 매일 일하러 들어오는 화면에서 창부터 닫아야 하는 것은 비용이다. 안내는 필요할 때 찾는 것이지
  들이미는 것이 아니다.
- **REVISIT WHEN** 대표 외에 새 사용자가 이 OS 를 쓰기 시작할 때 (첫 로그인 1회 한정 노출은 재검토 가능).

## D-18 성과 지표는 새 표 없이 이미 있는 기록에서 계산한다

- **DECISION** `src/services/kpiService.ts` 는 수금·업무·자금 신청·활동 기록·업무 일기에서 거꾸로 지표를 만든다. 근거 5건 미만은 '기준선 만드는 중', 잴 수 없는 것은 '측정 방법만 정함' 으로 표시한다. 목표치 필드는 아예 없다.
- **WHY** 규격 v3.0 §4.2 — 실측 전 개선율을 지어내지 않는다. 그리고 지표를 위해 새 표를 만들면 대표가 입력할 것이 하나 더 는다. 이미 남기는 기록만으로 잴 수 있는 것부터 잰다.
- **WHY NOT ALTERNATIVE** `kpi_snapshots` 표에 매일 값을 쌓는 방식은 마이그레이션(사람 작업)이 필요하고, 첫 값이 쌓이기 전까지 화면이 비어 있다. 지금 방식은 오늘 당장 값이 나온다. 추이가 필요해지면 그때 스냅샷을 추가한다.
- **REVISIT WHEN** 같은 지표를 주 단위 추이로 보고 싶어질 때 (12주 실증 시작 시점).

## D-19 대표↔직원 역할 전환 화면과 PC↔모바일 미리보기 토글은 만들지 않는다

- **DECISION** 규격 v2.0(§13·§14)의 Role Switcher / Device Preview Switcher 는 이번 제품에 넣지 않는다.
- **WHY** 사용자가 대표 한 사람이다. 직원 계정이 없는데 "직원 화면" 을 보여주면 시연용 가짜가 된다(규격 §16 NOT BUILDING · Q-6 Placeholder 금지). 모바일은 미리보기가 아니라 실제 휴대폰에서 매일 쓰는 화면이라 토글 대신 반응형 자체를 QA 한다(8폭 × 글자 1.3배).
- **WHY NOT ALTERNATIVE** 역할을 흉내 내는 토글은 권한(RLS) 과 무관한 화면 장식이 되어 "권한이 다르다" 를 오히려 잘못 보여준다.
- **REVISIT WHEN** 두 번째 사용자(직원)가 생겨 `can_write_workspace` 가 실제로 갈리는 순간 — 그때는 실제 계정으로 로그인해 보는 것이 미리보기다.

## D-20 AI 는 이번 단계에 넣지 않는다 — 규칙으로 충분한 곳에 AI 를 붙이지 않는다

- **DECISION** 우선순위·경고·하루 정리·이벤트 우선순위는 전부 규칙이며, 화면 어디에서도 "AI" 라 부르지 않는다. LLM 자리는 '향후 확장' 에 NEXT 로만 둔다.
- **WHY** 규격 v3.0 §6 — Rule 이면 충분한데 AI 로 포장하면 Strategic P0. 규칙이라 "왜 이것이 위인가" 를 한 줄로 설명할 수 있다(오늘 화면의 이유 표기).
- **WHY NOT ALTERNATIVE** LLM 요약을 지금 붙이면 어떤 기록을 근거로 했는지 보여주는 장치부터 필요하고, 그 장치 없이는 근거 없는 요약이 된다.
- **REVISIT WHEN** 하루 기록이 평균 10건을 넘어 목록만으로는 읽기 어려워질 때.

## D-21 기획의도·성과 지표·향후 확장은 메뉴에서 찾을 수 있어야 한다

- **DECISION** 사이드바에 '이 시스템' 그룹(기획의도 `/why` · 성과 지표 `/kpi` · 향후 확장 `/roadmap`)을 둔다. 향후 확장은 NEXT 배지를 달고, 누르면 404 대신 "무엇을·왜 지금은 아닌지·언제 다시 볼지" 시트가 열린다.
- **WHY** 규격 v3.0 §24·Q-7·U-3 — Why AX 와 확장 층이 "존재하지만 찾을 수 없는" 상태는 Product Devil 항목이다.
- **WHY NOT ALTERNATIVE** 오늘 화면에 배너로 두면 매일 보는 화면이 무거워진다. 접히는 그룹이면 필요할 때만 연다.
- **REVISIT WHEN** 없음.

## D-22 파일 올리기의 형식·크기 제한을 앱에서 걸지 않는다 — 상한은 저장소 한 곳에서만 정한다

- **DECISION** 내부 OS·고객 플랫폼 양쪽에서 파일 선택창의 형식 제한(`accept`)과 앱 안의 크기 검사를 없앤다.
  저장소 버킷 `client-documents` 는 `allowed_mime_types = null` · `file_size_limit = null`
  (`supabase/migrations/20260906000011_storage_open_types.sql`). 실제 상한은 Supabase 프로젝트 전역
  설정 한 곳에서만 정한다. 예외는 '서류에서 불러오기'(OCR) 한 곳 — 거기는 보관이 아니라 판독이라
  PDF·이미지만 의미가 있다.
- **WHY** 실제 업무 파일은 한글(HWP)·워드·엑셀·압축파일이고, 스캔본은 10MB 를 쉽게 넘는다.
  더 큰 문제는 어긋남이었다: 고객 플랫폼은 `.hwp/.docx/.xlsx` 를 고를 수 있게 열어 두었는데 저장소가
  그 형식을 거부해, 고객이 한글 파일을 고르면 조용히 실패했다. 제한이 세 군데(앱 `accept` · 앱 크기검사 ·
  버킷)에 흩어져 있으면 어느 것이 막았는지 알 수 없다.
- **WHY NOT ALTERNATIVE** 형식 목록을 늘려 가며 유지하는 방식은 다음 형식이 나올 때마다 배포가 필요하고,
  같은 어긋남이 반복된다. 실행파일 차단은 형식 목록과 달리 안전 문제라 진단 첨부에서만 유지한다.
- **안전** 버킷은 여전히 비공개(`public = false`)이고 RLS·경로 규칙은 그대로다. 푼 것은 "무엇을" 이지
  "누가" 가 아니다. 올리기가 막히면 영어 메시지 대신 무엇 때문인지 한국어로 알린다.
- **REVISIT WHEN** 저장소 사용량이 요금제 한도에 가까워질 때 (그때는 전역 설정 한 줄로 조인다).

## D-23 좁은 화면에서는 줄을 나눈다 — 글자 칸과 고정폭 컨트롤을 한 줄에 두지 않는다

- **DECISION** 한 줄짜리 flex 안에 글자(`flex-1`)와 고정폭 컨트롤(`shrink-0` 버튼·select·date)을
  같이 두지 않는다. 좁은 폭에서는 글자 쪽에 `w-full sm:w-auto sm:flex-1` 을 주어 줄을 나누고,
  데스크톱 한 줄 배치가 필요하면 감싼 칸에 `sm:contents` + 자식 `order-*` 로 되돌린다.
  자동 검사(`npm run qa:squeeze`)가 360/390/430 과 글자 1.3배에서 이를 지킨다.
- **WHY** `flex-1` 은 기준폭이 0 이라 `flex-wrap` 이 있어도 줄이 넘어가지 않는다. 글자 칸만
  20~60px 로 눌려 한 줄에 한 글자씩 세로로 흐른다. 대표가 휴대폰에서 실제로 겪은 증상이고,
  스크린샷을 사람이 들여다봐야만 보이던 종류라 눈으로만 막을 수 없었다.
- **WHY NOT ALTERNATIVE** `min-w-[…]` 로 최소폭을 주는 방법은 화면폭·글자배율 조합마다 값이
  달라 결국 다시 넘친다. 줄을 나누는 쪽이 어느 폭에서도 성립한다.
- **REVISIT WHEN** 없음. 검사기가 남아 있는 한 회귀는 빌드 단계에서 잡힌다.

## D-24 위쪽 띠와 같은 이름의 큰 제목은 휴대폰에서 숨긴다

- **DECISION** `ScreenTitle` · `PageHeader` 가 현재 경로의 메뉴 이름과 제목을 비교해, 같으면
  휴대폰에서 `sr-only` 로 돌린다(넓은 화면에서는 그대로 보인다). 다르면 그대로 둔다.
- **WHY** 띠에 '고객 운영', 바로 아래 큰 글자로 또 '고객 운영' 이면 같은 말을 두 번 하면서
  화면 한 뼘(약 90px)을 먹는다. 휴대폰에서 그만큼 본문이 밀린다.
- **WHY NOT ALTERNATIVE** 화면마다 손으로 숨기면 이름을 바꿀 때 어긋난다. 비교해서 판단하면
  메뉴 이름이 바뀌어도 저절로 맞는다. 읽어 주는 기계에는 제목이 남으므로 접근성 손실도 없다.
- **REVISIT WHEN** 메뉴에 없는 경로가 늘어 띠가 브랜드명만 보여 주는 화면이 많아질 때
  (그때는 비교가 실패해 제목이 그대로 보이므로, 지금도 안전한 쪽으로 기운다).

## D-25 색은 두 갈래로만 쓴다 — '어디인가'(메뉴·묶음 머리)와 '얼마나 급한가'(카드 바탕)

- **DECISION**
  1. **어디인가** — 왼쪽 메뉴 아이콘과 오늘 화면 묶음 머리의 작은 칩에만 8색 표(`--color-nav-*`)를 쓴다.
     자리가 정해져 있고 크기가 작아(20~28px) 본문과 섞이지 않는다.
  2. **얼마나 급한가** — 카드·숫자칸의 바탕을 아주 옅게(50/40~60% 투명도) 물들인다.
     마감 지남·수금 연체 = 빨강, 7일 이내 = 주황, 그 밖 = 흰색.
  업무 종류(특허·벤처인증 …)는 여전히 색으로 칠하지 않는다(점 하나만).
- **WHY** 흰 카드에 3px 선만으로 급한 정도를 말했더니 목록 전체가 똑같아 보였다. 게다가 업무 6개 ×
  서류 10종이라 거의 모든 업체가 "지금 N" 이 되어 전부 빨간 선이 붙었다. **다 빨가면 아무것도 안 빨갛다.**
  그래서 (a) 급한 정도의 기준을 경고 건수가 아니라 대표가 실제로 움직이는 것 — 다음 할 일의 마감과
  수금 연체 — 으로 바꾸고, (b) 선 대신 바탕을 옅게 깔아 목록의 정렬 순서와 색이 같은 방향을 보게 했다.
  위에서부터 색이 옅어지므로 어디까지가 급한지가 스크롤 없이 읽힌다.
- **WHY NOT ALTERNATIVE** 업무 종류마다 색을 주는 방식(무지개)은 정작 급한 것을 묻는다 —
  색이 '무엇'을 말하면 '언제'를 말할 자리가 없어진다. 지금은 색이 오직 시간만 말한다.
- **안전** 바탕은 글자 대비를 해치지 않는 선까지만(본문 대비 AA 유지). 테마 9종 검사 통과.
- **REVISIT WHEN** 업체가 30곳을 넘어 한 화면에 빨강이 다시 가득 찰 때 (그때는 '오늘 마감' 만 빨강으로 좁힌다).

## D-26 Tailwind 클래스 이름은 절대 이어 붙여 만들지 않는다

- **DECISION** `` `text-nav-${accent}` `` 같은 조립을 금지하고, 이름을 통째로 적은 표(Record)에서 꺼낸다.
  `navAccentClass` · `groupAccentClass` · `SECTION_CHIP` 이 그 형태다.
- **WHY** Tailwind 는 소스 파일에 적힌 글자를 그대로 훑어 CSS 를 만든다. 이어 붙여 만든 이름은
  소스 어디에도 없으므로 **CSS 자체가 생성되지 않는다.** 그래서 왼쪽 메뉴 아이콘 색이 처음부터
  단 한 번도 나온 적이 없었다(전부 흰색). 타입 검사도 린트도 이것을 잡지 못한다 — 문법은 멀쩡하다.
- **확인 방법** `npm run build` 뒤 `grep -o "\.text-nav-[a-z]*" dist/assets/*.css` 로 실제 생성 여부를 본다.
- **REVISIT WHEN** 없음.

## D-27 업체를 열면 회사 기본 정보가 접히지 않고 바로 보인다 — 단, 비밀번호는 어디에도 없다

- **DECISION** 업체 개요 화면에서 '회사 기본 정보' 를 접이식에서 꺼내 '지금 할 일' 바로 아래에 펼쳐 둔다.
  네 묶음으로 나눈다 — **회사**(설립일·업력·사업자등록번호·법인등록번호·업태·종목·주소),
  **사람**(대표자·담당자·상시근로자·주주 임원 구성), **연락처**, **인증서**.
  새 칸 세 개를 더했다: `representativeName`(대표자 이름 — 담당자와 분리), `employeeCount`(상시근로자 수),
  `shareholders`(주주·임원 구성).
- **WHY** 업체를 여는 이유의 절반은 "사업자번호가 뭐였지 / 설립이 몇 년도지 / 인증서 받았던가" 를
  확인하려는 것이다. 그때마다 접힌 칸을 한 번 더 펴야 했다. 상담 중에 한 번 더 누르게 만드는 것이
  곧 카톡을 뒤지게 만드는 것이다. 대표자와 담당자를 한 칸에 섞어 두었던 것도 갈랐다 —
  대표는 김대표인데 실무는 이과장이 하는 경우가 흔하다(예전 기록은 대표자 칸이 비면 담당자 이름으로 대신 보여 준다).
- **공동인증서 — 비밀번호는 저장하지 않는다.** 화면에는 '받음 · 발급일 · 보관 위치' 또는 '아직 안 받음' 만 나온다.
  비밀번호를 여기 두면 이 화면을 여는 사람이 곧 고객사 계정을 쓸 수 있는 사람이 되고, 내려받은 백업
  파일(JSON)에도 평문으로 남는다. 그 위험은 "매번 물어보는 번거로움" 과 바꿀 만한 것이 아니다.
  계약 테스트가 어떤 칸의 key·label 에도 비밀번호/주민등록번호가 없음을 매 실행마다 확인한다.
- **WHY NOT ALTERNATIVE** 암호화해서 저장하는 방법도 브라우저에서 복호화하는 이상 열쇠가 같은 곳에
  있어야 하므로 실질적인 보호가 되지 않는다. 저장하지 않는 것만이 확실하다.
- **안전** 새 칸은 전부 선택 입력이고 기본값은 빈 문자열이다. 예전 기록은 읽을 때 자동으로 빈 값이 되며
  DB 변경도 없다(payload 에 그대로 실린다). 잃는 데이터 없음.
- **REVISIT WHEN** 개요가 너무 길어져 '지금 할 일' 이 묻힐 때 (그때는 사람·연락처 묶음만 접는다).

## D-28 서류에서 읽은 값은 '한 칸에 한 값' 으로 줄인다 — 그리고 어느 칸이든 손으로 적을 수 있다

- **DECISION**
  1. 사업자등록증의 '사업의 종류' 는 표다. 업태 칸의 중복(제조업 ×7)은 하나로 줄이고,
     종목은 대표 하나만 앞에 두고 나머지는 `businessItemsExtra` 로 뺀다(버리지 않는다).
  2. 주소는 **본점 소재지**를 먼저 쓴다. 사업장 소재지와 다르면 컨설팅에서 쓰는 것은 등기부상 본점이다.
  3. 회사 기본 정보의 모든 칸(인증서 제외)은 눌러서 그 자리에서 고칠 수 있다. 비어 있으면 '+ 입력'.
- **WHY** PDF 에서 글자를 뽑으면 표가 칸 단위로 이어 붙어 한 줄이 된다. 그대로 넣었더니 업태 칸에
  '제조업 제조업 … 종목 간판 및 광고물 제조업 … 전자세금계산서 전용 전자우편' 까지 들어가 화면이
  문단으로 뒤덮였다. 주소도 뒤의 '사업의 종류' 를 통째로 물고 들어왔다.
  원인은 라벨 자르기였다 — 국세청 인쇄물은 "본 점 소 재 지" 처럼 글자마다 띄어 인쇄하는데,
  라벨을 붙여 쓴 글자로 비교하고 있어 자르기가 통째로 실패했다. 이제 글자 사이 공백을 허용해 비교한다.
- **손으로 적을 수 있어야 하는 이유** 등록증이 없는 업체도 있고, 통화 중에 들은 값을 그 자리에서
  적어야 할 때가 더 많다. '서류에서 불러오기' 는 빠른 길일 뿐 유일한 길이어서는 안 된다.
- **WHY NOT ALTERNATIVE** 종목을 전부 한 칸에 넣고 화면에서 줄여 보여 주는 방법은, 복사했을 때
  다시 문단이 된다. 값 자체를 정리해 두는 편이 어디서 꺼내 써도 깔끔하다.
- **안전** 종목을 나누는 규칙은 '…업' 경계다. 나뉘지 않으면 통째로 한 항목으로 둔다(값을 잃지 않는다).
  새 칸은 선택 입력이고 기본값은 빈 문자열. DB 변경 없음.
- **REVISIT WHEN** '…업' 으로 끝나지 않는 종목이 흔해질 때.

## D-29 고객 목록은 표가 아니라 카드다 — 업무가 15개로 늘어도 가로로 밀지 않는다

- **DECISION** 데스크톱 현황표(가로 스크롤 표)를 없애고, 휴대폰·데스크톱이 같은 카드를 쓴다.
  업무는 카드 안에서 작은 조각(chip)으로 **줄바꿈**된다. 넓은 화면에서는 카드를 2열로 놓는다.
- **WHY** 업무가 6개일 때도 표는 가로 900px 를 넘겨 옆으로 밀어야 했다. 앞으로 15개까지 늘 수
  있으니 표를 유지하면 미는 거리만 길어진다. 조각을 줄바꿈시키면 6개는 두 줄, 15개는 네 줄이
  되고 **가로로는 어떤 폭에서도 넘치지 않는다.** 부품이 하나라 한쪽만 어긋날 일도 없다.
- **검증** `npm run qa:board` 가 업무를 15개로 늘린 뒤 가로 넘침이 없는지 매번 확인한다.
- **REVISIT WHEN** 업체가 50곳을 넘어 카드 목록이 너무 길어질 때 (그때는 접기·묶기를 검토한다).

## D-30 목록에서 바로 고친다 — 상태와 수금은 업체 안에 들어가지 않아도 된다

- **DECISION** 업무 조각을 누르면 상태 시트가, 미수금을 누르면 수금 시트가 그 자리에서 열린다.
  저장은 상세 화면과 **같은 함수**(`withService`·`withFee` → `saveClient`)를 쓴다.
- **WHY** "시작 전 → 진행 중" 한 번 바꾸려고 업체로 들어갔다 나오는 왕복이 하루에 수십 번이었다.
  목록이 곧 조작대여야 한다.
- **WHY NOT ALTERNATIVE** 목록용 사본을 따로 두고 나중에 합치는 방식은 상세 화면과 값이
  어긋날 수 있다. 같은 저장 함수를 쓰면 어긋날 자리가 없다.
- **안전** 먼저 화면을 바꾸고 저장에 실패하면 서버 값으로 되돌린다(토스트로 알린다).
  `qa:board` 가 새로고침 뒤에도 값이 남아 있는지 확인한다.

## D-31 '해당 없음' 을 되살린다 — 보류와 다른 뜻이다

- **DECISION** 업무 상태를 6단계로 되돌린다: 시작 전 · 진행 중 · 고객 회신 대기 · 완료 · 보류 ·
  **해당 없음**. 해당 없음은 가로선으로 지운 것처럼 흐리게 그리고, 진행률 분모에서 뺀다.
  언제든 다른 상태로 되돌릴 수 있다.
- **WHY** 보류로 합쳐 두었더니 "지금은 안 한다" 와 "이 회사에는 아예 없는 일" 이 한 칸에 섞였다.
  특허가 없는 회사에 특허가 '보류' 로 떠 있으면 언젠가 해야 할 일처럼 읽히고, 진행률도 영원히
  100% 가 되지 않는다. 법인설립·업종추가·특허·벤처인증 모두 해당 없는 회사가 실제로 있다.
- **데이터** 예전에 '해당 없음' 으로 저장해 둔 값은 저장된 글자가 처음부터 그대로였다
  (읽을 때만 보류로 바꿔 보여 주고 있었다). 이제 원래 뜻으로 되돌아온다 — 잃는 값 없음.
- **REVISIT WHEN** 없음.

## D-32 '클라우드로 옮기기' 안내는 정말 옮길 것이 있을 때만 뜬다

- **DECISION** 판단 기준을 "이 브라우저에 로컬 기록이 있느냐" 에서 **"아직 클라우드에 없느냐"** 로 바꾼다.
  `pendingLocalClients(cloud)` 가 클라우드 목록과 id 를 대조한다. '나중에' 는 그 id 들을
  `axmvp.ui.local_migration_dismissed` 에 기억해 다시 묻지 않는다.
- **WHY (원인)** 예전에는 로컬에 기록이 있기만 하면 무조건 띄웠다. 그런데 옮기고 나서도 브라우저
  원본은 **일부러 남겨 둔다**(백업이니까). 그래서 옮긴 뒤에도 새로고침할 때마다 같은 안내가 다시 떴다.
  '나중에' 는 `setLeftover([])` 로 화면 상태만 껐을 뿐 저장소를 건드리지 않아 다음 접속에 되살아났다.
  즉 두 단추 모두 "다시 안 뜨게" 하는 일을 하지 않고 있었다 — 안내가 늘 켜져 있는 것과 같았다.
- **WHY NOT ALTERNATIVE** 옮긴 뒤 로컬 원본을 지우는 방법은, 클라우드 저장이 실패했을 때 되돌릴 것이
  없어진다. 원본은 그대로 두고 **묻는 조건**을 고치는 쪽이 안전하다.
- **REVISIT WHEN** 없음.

## D-33 업체 삭제는 두 번 묻는다 — 두 번째는 이름을 적게 한다

- **DECISION** 업체 상세 → 더보기 → '업체 삭제'. 1차에서 무엇이 함께 사라지는지 숫자로 보여 주고
  보관하기·백업을 권한다. 2차에서 **업체 이름을 그대로 적어야** 버튼이 열린다.
- **WHY** 되돌릴 수 없는 일이다. "예" 두 번은 습관으로 눌린다. 이름을 적게 하면 지금 무엇을 지우는지
  한 번은 읽게 된다. 숫자(업무·서류·수금·메모·활동)를 보여 주는 것은 "이거 별거 없겠지" 를 막는다.
- **WHY NOT ALTERNATIVE** 목록에서 바로 지우는 단추는 잘못 누르기 쉬워 두지 않았다. 대신 보관하기가
  목록 정리용으로 남아 있다(기록은 보존).

## D-34 업체 상태는 계약 단계 3가지 — 저장 값은 그대로 둔다

- **DECISION** 화면에 보이는 업체 상태를 **계약 전 · 계약 완료 · 계약 종료** 셋으로 줄인다.
  저장 값은 예전 네 가지(`active`/`waiting`/`paused`/`completed`)를 그대로 쓰고 읽는 자리에서 옮긴다.
  `계약 전 ↔ waiting` · `계약 완료 ↔ active`(예전 `paused` 포함) · `계약 종료 ↔ completed`.
- **WHY** 예전 네 가지 중 진행 중·고객 대기·일시 중지는 **업무별 상태와 겹쳐** 같은 말을 두 군데서
  하고 있었다. 업체 수준에서 정말 갈라야 하는 것은 "계약을 했는가" 하나다.
- **WHY 저장 값을 안 바꾸나** DB 에 `check (status in ('active','waiting','paused','completed'))` 제약이
  걸려 있다. 새 값을 쓰려면 사람이 SQL 을 한 번 더 돌려야 하는데, 화면 문구 하나 때문에 그럴 이유가 없다.
  계약 테스트가 "저장 값이 제약이 받는 범위 안" 인지 매번 확인한다.
- **REVISIT WHEN** 계약 단계가 넷 이상 필요해질 때 (그때는 제약을 넓히는 마이그레이션을 함께 낸다).

## D-35 오늘 화면 맨 위는 '내가 적은 할 일' 이다 — 규칙이 센 숫자가 아니라

- **DECISION** 오늘 화면의 큰 제목을 `반드시 처리할 것 N건`(규칙 경고 합계)에서
  `오늘 할 일 N건`(대표가 직접 적은 것)으로 바꾼다. 그 아래 첫 묶음도 '오늘 할 일' 이고,
  규칙이 찾은 '지금 이것부터' 는 그 다음으로 내린다.
  '오늘 반드시' 로 세는 경고에서 **서류 없음·서류 만료를 뺀다**(마감·수금·자금 신청만 남긴다).
- **WHY** 대표 의견 — "반드시 처리할 것 12건" 의 대부분이 아직 안 받은 서류였다. 서류는 요청해 두면
  며칠 걸리는 일이지 오늘 당장의 일이 아니다. 업무 6개 × 서류 10종이라 이 숫자는 늘 두 자리가 되고,
  **매일 두 자리인 숫자는 아무 뜻도 없다.** 정작 하루를 굴리는 것은 "누구에게 전화할지" 같은
  내가 적어 둔 한 줄이다.
- **안전** 서류 경고 자체는 없애지 않았다. 등급만 critical → warning 으로 내리고, 업체 상세와
  '지금 챙길 것' 목록에서는 그대로 보인다.
- **REVISIT WHEN** 할 일을 아무도 안 적어 맨 위가 늘 비어 있을 때 (그때는 적게 만드는 쪽을 고친다).

## D-36 할 일은 새 표를 만들지 않는다 — 업무 일기의 '할 일' 하나로 쓴다

- **DECISION** 오늘 화면·일정 화면·일기 화면이 모두 `ops_journal_entries` 의
  `follow_up`(화면 이름 '할 일') 항목을 읽고 쓴다. 새 표도, 새 저장소도 만들지 않았다.
  일정 화면의 각 날짜에 '할 일 적기' 칸이 있고, 업체 마감 줄의 `+` 는 그 마감을 내 할 일로 옮긴다.
- **WHY** 같은 것을 두 곳에 저장하면 반드시 어긋난다. 한 표를 쓰면 어디서 적든 어디서든 보인다 —
  대표 요청("일정에서 적어도 여기에 다 기록됐으면") 이 곧 이 구조다.
- **WHY NOT ALTERNATIVE** 별도 todo 표는 일기와 중복되고, 나중에 "그날 무슨 일이 있었나" 를 볼 때
  두 곳을 합쳐 봐야 한다.
- **검증** `npm run qa:todos` 가 오늘↔일정 양방향으로 같은 항목이 보이는지 매번 확인한다.

## D-37 '한동안 조용한 업체' 를 알린다 — 컨설팅에서 실제로 놓치는 것

- **DECISION** 활동 기록·메모·수정 시각 중 마지막에서 `QUIET_DAYS`(30일)가 지나면 참고 등급
  경고를 낸다. 계약 전 업체도 대상이다.
- **WHY** 마감이 지난 일은 어차피 빨갛게 뜬다. 정작 놓치는 것은 **아무 경고도 안 뜨는 업체** —
  마감도 없고 서류도 다 있으면 목록 아래로 조용히 가라앉았다가 몇 달 뒤에 "그 회사 어떻게 됐지"
  가 된다. 계약 전 업체가 특히 그렇다.
- **WHY NOT ALTERNATIVE** 성사 확률·다음 단계 추천 같은 것은 지어내는 값이 된다(규격 §4.2).
  "며칠 조용했다" 는 기록에서 그대로 세는 값이라 지어내는 부분이 없다.

## D-38 자주 쓰는 할 일 문구는 시작점만 준다

- **DECISION** 할 일 적는 칸에 8개 문구 칩(통화·서류 요청·서류 확인·신청서·접수·결과 확인·보고·청구)을
  둔다. 누르면 앞부분만 채우고 뒷말은 사람이 쓴다. 그대로 저장되지 않는다.
- **WHY** 컨설팅은 같은 동작이 업체만 바꿔 가며 반복된다. 매번 처음부터 타자를 치면 결국 기록을
  안 남기게 된다. 다만 문구를 통째로 저장하면 무슨 뜻인지 없는 기록이 쌓이므로 시작점까지만 준다.

## D-39 '서류가 없어 막혔다' 는 경고가 아니다 — 업체 안에서 조용히 표시한다

- **DECISION** `blocked_missing_doc` 경고를 **없앤다**(종류 자체를 지웠다). 대신
  서류 탭에서 아직 안 받은 서류에 작은 빨간 점을 찍고, 업무 카드에는 회색 배지(`서류 N`)와
  회색 안내 판('아직 안 받은 서류')만 둔다. 목록 화면의 업무 조각에서도 '서류 없음' 을 뺐다.
- **WHY** 대표 의견 — 서류는 요청해 두면 며칠 걸리는 일이지 '지금 해야 할 일' 이 아니다.
  업무 6개 × 서류 10종이라 이 경고만으로 경고 목록이 가득 찼고, 정작 마감이 묻혔다.
  **서류는 해야 할 일이 아니라 상태다.** 상태는 그 물건이 있는 자리(서류 탭)에서 보여야 한다.
- **남긴 것** `missingDocumentsFor` 는 그대로다 — 화면이 그 표시를 그릴 때 쓴다.
  유효기간이 지난 서류(`doc_expired`)는 경고로 남는다(그건 시간이 만든 일이라 마감에 가깝다).
- **REVISIT WHEN** 없음.

## D-40 할 일은 체크상자가 아니라 이름 있는 선택지로 바꾼다

- **DECISION** 할 일 왼쪽의 체크상자를 없애고, 누르면 **진행 중 / 완료 / 내일로 미루기 / 삭제**
  네 가지를 이름과 설명으로 보여 주는 시트를 연다. 관련 업체가 있으면 '업체 열기' 도 그 안에 있다.
- **WHY** 대표 의견 — "눌러보고 나서야 알았다". 체크상자는 눌러 보기 전에는 무슨 일이 일어나는지
  알 수 없다(완료인지 삭제인지). 이름을 붙여 고르게 하면 누르기 전에 안다.
- **'내일로 미루기' 를 넣은 이유** 오늘 못 한 일을 그냥 두면 다음 날 목록이 밀린 것으로 뒤덮인다.
  미루는 것도 정직한 처리이고, 미룰 수 없으면 사람은 그냥 지운다.
- **줄에서 화살표를 뺀 이유** 360px + 글자 1.3배에서 화살표 단추가 글자 칸을 110px 로 눌렀다.
  업체로 가는 길은 시트 안으로 옮겼다.

## D-41 업무 카드는 넓은 화면에서 2열 — 펼친 카드만 두 열을 쓴다

- **DECISION** 업체 상세의 진행 업무를 `xl` 이상에서 2열 격자로 놓는다. 접힌 카드는 한 칸,
  펼친 카드는 `col-span-2` 로 두 칸을 쓴다. 상태 고르는 칸은 `sm` 이상에서 제목 옆으로 붙인다.
- **WHY** 카드 하나에 들어가는 것은 제목 한 줄 + 다음 할 일 한 줄이 전부인데 1400px 를 가로로 다
  쓰면 글자 사이가 텅 비어 오히려 읽기 어렵다. 대표 표현으로 "뒤죽박죽" 이다.
  펼치면 날짜·메모·서류가 들어와 폭이 필요하므로 그때만 두 칸을 쓴다.
- **휴대폰** 그대로 1열이다. 좁은 폭에서 2열은 어느 쪽도 못 읽는다.

## D-42 오늘 할 일이 화면에서 가장 큰 덩어리다

- **DECISION** 오늘 화면의 '오늘 할 일' 을 브랜드색 테두리 패널로 감싸고 제목을 `t-page` 크기로
  키운다. 안에서 **밀린 것 / 오늘 것 / 끝낸 것(접힘)** 셋으로 나눈다.
- **WHY** 하루를 굴리는 것은 내가 적은 한 줄이다. 크기가 곧 우선순위이므로 가장 커야 한다.
  끝낸 것을 접는 이유 — 남은 일이 목록의 전부여야 "다 했나" 를 한눈에 안다.

## D-43 업체 안에서도 그 자리에서 할 일을 적는다

- **DECISION** 업체 상세 개요에 할 일 적는 칸을 둔다. 업체는 자동으로 붙는다.
- **WHY** 상담하다 "그럼 다음 주에 서류 주세요" 가 나오면 그 자리에서 적어야 한다.
  일기 화면으로 옮겨 가야 하면 십중팔구 안 적는다.

## D-44 컨설팅 작업실은 코드만 main 에 올리고, 표는 아직 올리지 않는다

- **처음 결정** 특허 × 벤처 × MVP 워크플로 엔진은 `claude/patent-venture-mvp-studio-v1` 브랜치에서 만들고
  Preview 로만 확인한다(작업 지시가 "Preview 까지만" 이었다).
- **바뀐 결정 (2026-09-08, 대표 지시)** 브랜치를 main 으로 fast-forward 병합하고 푸시했다(`5268519`).
  D-16(main 직행)으로 돌아온 것이다. 되돌린 커밋도, 다시 쓴 이력도 없다.
- **그래도 표는 올리지 않았다** 마이그레이션 `20260908000012_consulting_studio.sql` 은 저장소에만 있고
  Production Supabase 에 **적용하지 않았다.** 적용은 사람이 SQL Editor 에서 한 번 실행해야 한다.
- **그래서 Production 에서 지금 무엇이 보이나** 사이드바에 '컨설팅 작업실' 이 생기고, 눌러 들어가면
  "READY — SQL 적용 후 사용" 안내만 보인다. 고객 상세의 '컨설팅' 탭도 같은 안내다. 오늘 화면의
  '컨설팅 다음 행동' 은 통째로 숨는다(빈 구역을 만들지 않는다). 기존 화면·데이터는 아무 영향이 없다.
- **왜 코드를 먼저 올려도 안전한가** 표 없음 감지(`isTablesMissing`)가 모든 읽기 경로를 감싼다.
  표가 없으면 오류 화면이 아니라 안내로 떨어지고, 쓰기는 애초에 시도되지 않는다. E2E 와 단위 테스트가
  이 경로를 고정한다.

## D-45 고객은 하나 — 컨설팅 프로젝트는 operations_clients 에 매달린다

- **DECISION** 두 번째 CRM 을 만들지 않는다. `consulting_projects.client_id → operations_clients(id)` (cascade).
  회사 기본 8항목은 프로젝트를 만들 때 고객 기록에서 사실표로 가져오되 상태는 '미확인', 출처는
  '고객 운영 기록' 으로 표시한다. 서류로 확인한 사람이 '확정' 으로 바꾼다.
- **WHY** 같은 회사의 대표자·번호·주소가 두 곳에 있으면 반드시 어긋난다. 사실표는 "숫자와 사실의 단일 원본"
  (Master §5)인데, 그 원본이 고객 기록과 싸우면 안 된다. 가져온 값에 상태를 붙이는 이유는 고객 기록의 값이
  OCR·수기 입력이라 서류 확인 전이기 때문이다.
- **WHY NOT ALTERNATIVE** AX STUDIO 의 `projects` 에 합치는 안 — 설문·진단 파이프라인과 단계 엔진은 화면·데이터가
  달라 강제로 합치면 양쪽이 어색해진다(CONSULTING_STUDIO_AUDIT §3).

## D-46 단계 상태·사실표·핵심 줄기는 프로젝트 한 행의 payload 에 둔다

- **DECISION** 표는 5개(projects · artifacts · prompt_packages · decisions · evidence). 단계 상태·사실표·핵심 줄기·
  게이트·참고자료 선택·특허/MVP/벤처/실사 작업공간은 `consulting_projects.payload` 안이다.
- **WHY** 프로젝트와 1:1 이고 한 화면에서 함께 자동저장된다. 따로 표로 나누면 절반만 저장되는 순간이 생기고,
  마이그레이션 미적용 환경 대응도 표 수만큼 늘어난다. 계속 늘어나는 목록(산출물·프롬프트·결정·증빙)만 표를 가진다.
- **REVISIT WHEN** payload 가 수백 KB 를 넘거나, 사실표를 프로젝트 밖(예: 고객 단위)에서 공유해야 할 때.

## D-47 LLM 은 부르지 않는다 — 프롬프트는 사람이 들고 나가고 결과는 붙여 넣는다

- **DECISION** 외부 AI API 호출 0. 프롬프트 꾸러미 13종 × 대상 4종을 결정론적으로 만들고(같은 입력 → 같은 출력,
  테스트로 고정), 복사·다운로드·"열기"(새 탭) 로 내보낸다. 결과는 붙여넣기/파일로 들여와 산출물 버전이 된다.
  결과 첫 줄에 `[ARTIFACT] type=… stage=…` 를 요구해 종류·단계를 자동 인식한다.
- **WHY** 요청의 명시 조건이자, 지금 이 제품에서 AI 를 붙이면 생기는 것은 비용과 "AI 가 판단했다" 는 과장뿐이다.
  규칙 계산(다음 행동·게이트·낱말 겹침)을 AI 라 부르지 않는다(Master §18-2).
- **SCOPED ACTIVATION** Master 5,874줄을 프롬프트에 넣지 않는다. 종류마다 규칙 20~40줄만 싣는다.
  테스트가 프롬프트 길이 상한(9,000자)을 지킨다.

## D-48 밖으로 나가는 텍스트는 개인정보 필터를 거친다 — 법인등록번호는 예외

- **DECISION** 프롬프트·Context 를 만들 때 주민번호·계좌번호·비밀번호 줄·인증서 비밀번호·API 키(sk-/sb_secret_/
  AKIA/ghp_/JWT)·이메일·휴대폰을 `[가림:종류]` 로 바꾸고 개수를 배지로 보여 준다. 저장되는 것도 필터 통과본뿐이다.
- **법인등록번호** 는 주민번호와 모양(6-7자리)이 같다. "법인(등록)번호" 라벨이 앞에 붙은 것은 회사 공개 정보이므로
  가리지 않는다(필터가 잠시 하이픈을 바꿔 두었다가 되돌린다). 라벨 없이 홀로 있는 13자리는 주민번호로 보고 가린다 —
  틀리면 덜 가리는 쪽보다 더 가리는 쪽이 안전하다.
- **한계** 정규식이다. 이름·주소 같은 자유 텍스트 PII 는 잡지 못한다. 미리보기가 "실제로 복사되는 내용" 인 이유다.

## D-49 다음 행동은 규칙이 정하고 최대 3개다

- **DECISION** 막힘 → 게이트 미결 → 현재 단계의 빈 필요 사실 → 필요 산출물(없으면 프롬프트 만들기 / 프롬프트는
  있는데 결과가 없으면 들여오기) → 참고자료 2~5종·PDF → 최신 기준 확인(K9) → 단계 완료. 같은 입력이면 같은 출력.
- **WHY** Master 의 "이번엔 뭐 할 차례야?" 에 대한 답을 사람이 매번 다시 조합하지 않게 하려는 것이 이 화면의 존재
  이유다(K6·§55). 3개를 넘기면 다시 목록이 된다.
- **점수 없음** GO/HOLD/NO-GO 는 9개 체크를 사람이 표시하고 결정도 사람이 고른다. 코드는 "GO 근거 N/9" 만 센다.
  Judge 10축도 사람이 매긴다. 가짜 AI 점수를 만들지 않는다.

## D-50 기본 화면은 "지금 할 일" 하나다 — 12탭은 `?adv=1` 뒤로

- **DECISION** `/studio/:id` 기본은 간단 모드(진행하기·결과물·기록 3탭)다. 기존 12탭은 지우지 않고
  `?adv=1` 로 옮겼다. 화면은 `CurrentTask` 객체 하나만 렌더링하고, 단계·프롬프트 종류·산출물 종류를 모른다.
  행동은 7가지뿐이다: 확인 · 고르기 · 입력 · 올리기 · 프롬프트 만들기 · 결과 가져오기 · 계속하기.
- **WHY** 12탭은 엔진의 내부 구조를 그대로 화면 이름으로 쓴 것이었다. 사용자가 `PATENT_SPEC_DRAFT` 와
  `PATENT_CLAIMS_REVIEW` 의 차이를 알아야 프롬프트를 만들 수 있었다. 17단계가 사람을 안내해야지,
  사람이 17단계를 관리해서는 안 된다.
- **HOW** ENGINE LAYER(기존) + OPERATOR LAYER(신규 `currentTask.ts` · `applyTask.ts`). resolver 는 순수 함수라
  같은 상태면 id 까지 같다(단위 테스트가 고정). 단계 전환은 `autoAdvance` 가 하고, 사람에게 묻는 것은
  되돌릴 수 없거나 사실 확인이 필요한 4곳뿐이다(게이트·출원·신청·P0 확인).
- **숨김 ≠ 삭제** 엔진·DB·타입·RLS·테스트 무수정. E2E 가 12탭·S0~S16·사실표 값이 살아 있음을 매번 확인한다.
- **REVISIT WHEN** 간단 모드만으로 한 프로젝트를 끝까지 밀어 본 뒤. 고급 보기를 거의 안 쓰게 되면 그때 정리한다.

## D-51 LLM 결과는 구조화 블록으로 돌아오고, 못 알아봐도 원문은 반드시 남는다

- **DECISION** 프롬프트 끝에 `--- MIRAE_OS_RETURN ---` 블록(TYPE·SUMMARY·DECISION_OPTIONS·MISSING_FACTS·
  NEXT_RECOMMENDATION)을 요구한다. 돌아온 답을 붙여 넣으면 요약·후보·부족한 사실을 읽어 다음 화면
  ("어느 방향으로 갈까요?")까지 이어 간다. 사용자는 종류·단계·버전을 고르지 않는다.
- **파싱 실패는 실패가 아니다** 블록이 없으면 원문을 그대로 산출물로 저장한다. 형식을 강제해 데이터를 잃는 것보다
  형식 없이 남기는 편이 낫다. E2E 가 이 경로를 고정한다.
- **저장은 원문 그대로** 블록을 지우고 저장하면 후보를 다시 읽을 수 없다. 사람이 읽는 화면에서만
  `stripReturnBlock` 으로 감춘다.
- **품질** 블록 요구는 프롬프트에 *더한* 것이지 뺀 것이 아니다. 길이 상한 9,000자는 그대로 지킨다(단위 테스트).

## D-52 회사 기본정보는 서류가 채운다 — 사업자등록증·법인등기부등본

- **DECISION** S0(회사 이해)의 입력·확인 화면에 "사업자등록증 · 법인등기부등본으로 채우기" 를 둔다.
  한 장만 올려도 되고 두 장을 한꺼번에 올려도 된다. 읽은 값은 목록으로 보여 주고 **체크한 것만** 채운다.
  비어 있던 칸은 미리 켜 두고, 이미 값이 있는 칸은 꺼 둔 채 "지금 적힌 「…」을(를) 바꿉니다" 를 함께 보여 준다(§44).
- **WHY** 회사명·대표자·설립일·본점·사업자등록번호·업종은 서류에 이미 적혀 있다. 이것을 손으로 일곱 번
  옮겨 적게 하는 것은 "입력 화면을 만드는" 일이지 "다음 행동을 만드는" 일이 아니다.
- **REUSE** 판독기(`docTextExtract`: PDF 텍스트 + 한국어 OCR)와 파서(`koreanDocParser`)는 고객 운영에서
  쓰던 것을 그대로 쓴다. 새로 만든 것은 **파서의 이름을 사실표 이름으로 옮기는 순수 함수** 하나뿐이다
  (`companyDocFacts.ts`).
- **두 장을 함께 올렸을 때** 항목마다 더 권위 있는 쪽을 쓴다. 등기부 = 법인등록번호·본점·회사성립연월일·
  상호·대표자. 등록증 = 사업자등록번호·업태·종목. 한 장뿐이면 그 한 장을 쓴다.
- **출처를 남긴다** 값의 `source` 가 '대표 확인' 이 아니라 '사업자등록증' / '법인등기부등본' 이 된다.
  나중에 근거를 다시 찾을 수 있어야 하기 때문이다.
- **옮긴 값과 읽은 값을 구분한다** 서류에 그대로 적힌 것은 '확정'. 주요 제품·서비스는 서류에 없고 종목에서
  옮긴 것이므로 '미확인' 으로 두어 확인 화면에서 눈에 띄게 한다. 없는 값(매출·직원수·거래처수)은
  파서가 돌려주지 않으므로 애초에 채워질 수 없다(§31).
- **읽는 것이 그 단계를 끝내지는 않는다** 확인 화면에서 서류를 다시 올려도 '맞아요, 계속' 을 누른 것으로
  치지 않는다. 값만 쓰고 다음 할 일은 resolver 가 다시 정한다.
- **한계** 파일은 읽고 버린다(보관하지 않는다). 서류 원본 보관은 고객 서류 탭(`client-documents`)의 일이다.
