## PASS 1 — 무엇이 복잡한가 (실측 감사)

지금 `/studio/:id` 는 탭 12개다. 각 탭이 엔진의 내부 구조를 그대로 화면 이름으로 쓰고 있다.

| 지금 화면 | 사용자가 알아야 하는 내부 개념 | 판정 |
|---|---|---|
| 탭 `단계` (291줄) | S0~S16, 상태 6종, exit checklist, 막힘/건너뛰기, 완료 게이트 | **내부 상태 직접 관리** — 숨긴다 |
| 탭 `사실표` (119줄) | 45항목 × 5상태 × 출처·기준일 | 필요한 것만 물어본다 |
| 탭 `핵심 줄기` (66줄) | 8칸 이름(Core Thread) | 자동 갱신 — 숨긴다 |
| 탭 `특허`·`MVP`·`벤처` (213+94+123줄) | 작업공간 전체 폼 | 단계별 질문으로 쪼갠다 |
| 탭 `증빙` (100줄) | 10슬롯 매트릭스 | "증빙 부족 2건" 행동으로 |
| 탭 `프롬프트` (212줄) | 종류 13 × 대상 4 직접 선택 | **원클릭** — 시스템이 고른다 |
| 탭 `산출물` (149줄) | 종류·버전·상태(draft/superseded) | 문서 목록으로 |
| 탭 `결정` (72줄) | kind 8종 직접 분류 | **자동 기록** |
| 탭 `실사` (153줄) | 7종 세트 | 단계 안내로 |
| 탭 `개요` (200줄) | 지표 4 + 경고 + 타임라인 + 접힘 4개 | Dashboard 병 — 걷어낸다 |

### 구체적 문제 (사용자가 실제로 부딪히는 것)

1. **첫 화면이 질문이 아니라 계기판이다.** 개요를 열면 숫자 4칸·경고·핵심 줄기 8줄·단계 17칸·접힘 3개가 한꺼번에 뜬다. "지금 뭘 하지?" 의 답이 화면 어딘가에 있지만 찾아야 한다.
2. **프롬프트를 만들려면 3번 이동한다.** 개요 → 프롬프트 탭 → 종류 13개 중 고르기 → 대상 4개 중 고르기 → 만들기. 사용자가 `PATENT_SPEC_DRAFT` 와 `PATENT_CLAIMS_REVIEW` 의 차이를 알아야 한다.
3. **결과를 저장하려면 종류·단계·버전을 고른다.** 시스템이 방금 그 프롬프트를 만들었는데도 다시 묻는다.
4. **단계 완료가 수동이다.** 산출물을 들여왔는데도 사용자가 `단계` 탭에 가서 체크리스트를 켜고 `완료로 넘기기` 를 눌러야 다음으로 간다.
5. **기록하려고 기록한다.** `결정` 탭에서 한 줄·이유·종류·단계를 직접 적는다.
6. **모바일에서 탭 12개가 가로 스크롤이다.** 390px 에서 `개요 단계 사실표 핵심 줄기 특허 M…` 까지만 보인다.
7. **빈 프로젝트의 첫인상이 "45개 칸을 채우라"** 다.

### 보존해야 하는 것 (숨김 ≠ 삭제)

엔진·DB·타입·테스트는 그대로 둔다: 단계 정의 17, 사실표 45, 게이트 6종, 다음 행동 resolver, 프롬프트 13종, 개인정보 필터, KIPO 118, 표 5개, RLS, 단위 138 + E2E 45.

## PASS 2 — 운영자 상호작용 모델

### 2-1. 계층

```
ENGINE LAYER      (기존 그대로)   workflowDefinition · factsheetSchema · gateEngine
                                  nextActionResolver · promptPackageBuilder · privacyFilter
OPERATOR LAYER    (신규)          currentTask.ts  ← 이 문서의 핵심
UI                (재설계)        지금 할 일 카드 하나 + 결과물 + 기록
```

UI 는 `CurrentTask` 객체 **하나**를 받아 렌더링한다. 화면이 단계를 알 필요가 없다.

### 2-2. CurrentTask

```ts
resolveCurrentTask(project, { artifacts, prompts, evidence, today }) → CurrentTask
```

```ts
{
  id            // 같은 상태 → 같은 id (테스트가 고정)
  stageKey      // 내부용. 화면에 S3 를 크게 쓰지 않는다
  headline      // "특허 아이디어를 확정할 차례입니다"
  detail        // 한 문장 설명
  actionType    // 아래 7종
  primaryAction // 버튼 글자 하나
  ready         // [{label, ok}] — "준비된 정보 8/9"
  ...payload    // actionType 별
  nextPreview   // "다음: 선행기술 검토"
}
```

### 2-3. Action Type 7종 — UI 는 이것만 그린다

| type | 화면 | 예 |
|---|---|---|
| `CONFIRM` | 시스템이 이해한 내용 나열 + [맞아요, 계속] / [수정] | "회사 기본정보를 이렇게 이해했습니다" |
| `SELECT` | 선택지 3~6개 + 직접 입력 | "가장 중요한 문제는?" |
| `INPUT` | **부족한 칸만** 1~3개 | "두 가지만 확인하면 됩니다: 최근 매출 / 직원수" |
| `GENERATE_PROMPT` | 한 줄 설명 + [GPT 프롬프트 만들기] | 종류는 시스템이 안다 |
| `IMPORT_RESULT` | [붙여넣기] / [파일] | 종류·버전 자동 |
| `UPLOAD` | 파일 올리기 | 참고자료 PDF |
| `CONTINUE` | [계속하기] | 확인만 하면 되는 지점 |

### 2-4. 자동 부작용 (§43)

사용자가 한 번 누르면 뒤에서 함께 처리한다:

```
SELECT 핵심문제  → factsheet.coreProblem · coreThread.fieldProblem
                 → decision 기록 → S2 완료 → S3 활성 → timeline
IMPORT 결과      → artifact(종류·버전 자동) → decision → 해당 단계 완료 → 다음 단계 → timeline
INPUT 출원번호   → patent.filingStatus=filed · factsheet.patent → S7 완료 → timeline
```

사용자는 다섯 화면을 더 돌지 않는다.

### 2-5. 자동 단계 전환 규칙 (§19)

필요 사실 + 필요 산출물이 모두 갖춰지면 **exit checklist 를 묻지 않고** 완료한다.
단, 되돌릴 수 없거나 사실 확인이 필요한 곳만 한 번 묻는다(§20):

- S1 게이트 결정 (사람이 고른다)
- S7 출원 완료 (출원번호가 사실인지)
- S14 신청 완료
- S13 P0 확인 (12개는 사람이 확인해야 하는 항목)

그 외 S0·S2·S3·S4·S5·S6·S8·S9·S10·S11·S12·S15·S16 은 조건 충족 시 자동.

### 2-6. 화면 구조

```
/studio            프로젝트 목록 — 누구 / 어디까지 / 지금 무엇 / [계속하기]
/studio/:id        간단 모드 (기본)
                     ├ 진행하기   ← 지금 할 일 카드 하나 (첫 화면)
                     ├ 결과물     ← 특허/MVP/벤처로 묶은 문서
                     └ 기록       ← 읽는 타임라인
/studio/:id?adv=1  고급 보기 — 기존 12탭 그대로
```

모바일: 탭 3개는 390px 에 들어간다. 가로 스크롤 없음.

### 2-7. 프롬프트 (§12~15)

- 사용자는 종류를 고르지 않는다. `currentTask.promptType` 이 정한다. 대상 기본 = ChatGPT.
- 생성 후 기본은 **접힌 상태**: 제목 + [복사] [ChatGPT 열기] [Claude 열기] [내용 보기].
- 품질은 그대로. 오히려 `MIRAE_OS_RETURN` 블록 요구를 추가해 되돌아올 때 구조를 얻는다.

### 2-8. 구조화 반환 (§17)

프롬프트 끝에 요구:

```
--- MIRAE_OS_RETURN ---
TYPE: PATENT_IDEA
SUMMARY: 한 문단
DECISION_OPTIONS:
1) ...
2) ...
MISSING_FACTS:
- 최근 매출
NEXT_RECOMMENDATION: ...
--- END_MIRAE_OS_RETURN ---
```

파싱 성공 → 요약·선택지·부족한 사실을 화면에 보여주고 선택까지 이어 간다.
**파싱 실패 → 원문을 그대로 산출물로 저장한다(반드시).**

### 2-9. 사실 정확성 (§31·§32)

- 내부 상태 5종은 유지. 화면 표기: 확인됨 / 확인 필요 / 계획 / 시연용 / 향후.
- 자동 추정 금지: 매출·직원수·거래처수·계약·특허상태·투자·발명자·출원인·자체개발·점유율.
  이 값들은 CONFIRM 화면에 **"확인 필요"** 로 뜨고 사용자가 고쳐야 넘어간다.
- 안전한 기본값은 묻지 않는다(§33): workflow · owner · workspace · title · stage · artifact type · prompt type · version · timestamp.

### 2-10. 색·타이포 (§35·§36)

기존 디자인 시스템 그대로. 단계별 색 금지. brand + 무채색, 급할 때만 danger/warning/success.
본문 `t-body`(16px), 카드 제목 `t-card`, 큰 제목 `t-page`. `text-xs` 신설 금지.

### 2-11. 목표 (§45·§46)

| 상황 | 목표 클릭 |
|---|---|
| 새 프로젝트 → 첫 프롬프트 | 5~8 |
| 정보 충분한 고객 | 3~5 |
| 다음 단계 프롬프트 | 1~3 |
| 결과 가져오기 | 2~3 |

프로젝트 열기 → 다음 LLM 작업 준비: 30초.

E2E 가 클릭 수를 실제로 센다(`qa:simple`).

## PASS 8 — 무엇을 고급 보기로 옮겼는가 (숨김 ≠ 삭제)

기본 화면에서 사라진 것과, 그것이 지금 어디에 있는지:

| §3 이 숨기라고 한 것 | 지금 위치 | 사라지지 않았음을 무엇으로 확인했나 |
|---|---|---|
| S0~S16 직접 관리 | `?adv=1&tab=stages` | E2E `48 단계 데이터가 살아 있다 (S0~S16)` |
| 단계 상태 수동 변경 · 완료/검토대기/막힘/건너뛰기 버튼 | `?adv=1&tab=stages` | 같은 탭에 그대로. 간단 모드에는 버튼 없음 |
| 사실표(45항목 × 5상태) | `?adv=1&tab=factsheet` | E2E `48 사실표 데이터가 살아 있다` |
| 핵심 줄기 8칸 | `?adv=1&tab=thread` | E2E `44 …고급에서 고칠 수 있다` |
| 증빙 10슬롯 | `?adv=1&tab=evidence` | E2E `48 고급: 증빙 탭 보존` |
| 결정 로그 직접 작성 | `?adv=1&tab=decisions` | E2E `48 고급: 결정 탭 보존` |
| 프롬프트 종류 13 × 대상 4 선택 | `?adv=1&tab=prompts` | 간단 모드에 `<select>` 0개 (E2E `2 프롬프트 종류 선택 상자가 없다`) |
| 산출물 종류·버전·상태 | `?adv=1&tab=artifacts` | E2E `44 간단 모드로 저장한 산출물이 고급에도 있다` |
| 긴 체크리스트(실사 7종) | `?adv=1&tab=review` | 12탭 전부 유지 (E2E `48 고급 보기에 기존 12탭이 그대로 있다`) |

전환은 오른쪽 위 **[고급] / [간단히]** 한 번. URL `?adv=1` 이므로 링크로 공유할 수 있고, 새로고침해도 유지된다.
DB·서비스·타입·엔진은 한 줄도 지우지 않았다. 간단 모드는 **읽기 층이 아니라 쓰기 층**이다 — 여기서 넣은 값이
그대로 사실표·핵심 줄기·결정 로그에 들어간다(그래서 위 표의 마지막 칸이 성립한다).
