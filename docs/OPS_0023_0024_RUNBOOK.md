# 운영 DB 0023 · 0024 적용 안내서

> 대표가 Supabase SQL Editor 에서 **직접** 실행한다. 개발 쪽은 운영 DB 에 아무것도 실행하지 않는다(대표 승인 전 금지).
> 모든 파일은 로컬 PostgreSQL 16 에서 같은 순서로 연습해 통과했다 — `sudo bash scripts/db-local/run-0024-customer.sh`(`npm run qa:db` 안).
> 운영 Supabase 자체에서는 아직 한 번도 돌려 보지 않았다 — 아래 '기대 결과' 와 다르면 그 단계에서 멈추고 화면을 보낸다.

## 0. 한눈에

## 1. 선행 조건 — 모두 ✓ 여야 시작

- [ ] **점검** `supabase/manual/check_applied_0016_0024.sql` → 0016 ~ 0022 일곱 줄이 모두 **들어감**.
  - '없음' 이 있으면 그 번호부터 순서대로 먼저 적용한다(각각 대표 승인 · 파일 머리 안내대로). 그 뒤 이 안내서를 처음부터.
  - 0022(AI 사용량 장부)가 없어도 0024 는 들어가지만 '고객 AI 한도 없음 금지' 장치만 빠진다 → 0022 를 적용한 뒤 0024 를 한 번 더 실행하면 붙는다.
- [ ] **적용 전 점검** `supabase/manual/precheck_0023_0024.sql` → '판정' 칸에 **멈춤 0**.
  - **11번 '대표가 팀장 작업공간 구성원' 숫자를 적어 둔다** — 적용 뒤 확인 7번과 같아야 한다(팀장 화면 전환 그대로라는 뜻).
  - 7 · 8번(바꿀 함수 지문)이 '0020 그대로' 여야 한다. '다름' 이면 누가 운영에서 고친 본문이다 → 멈추고 §2-③ 으로 본문을 보관한 뒤 대표 확인.
    (D-597 · 2026-11-11 실제로 겪음) SQL Editor 는 붙여 넣을 때 줄 앞에 빈칸을 더해 본문이 계단처럼 밀린다 — 띄어쓰기 · 줄바꿈만 다른 본문은 이제 '0020 그대로' 로 본다(⑤ 의 0024 본문 확인도 같음). 글자가 하나라도 다르면 여전히 '다름 · 멈춤'.
  - 15 · 16번(이미 섞였을 수 있는 기록)은 '참고' — 적용과 무관하다. 0 이 아니면 §4-④.
- [ ] **백업 확인**(§2).
- [ ] **조용한 시간** — 대표 · 팀장 둘 다 저장 중이 아닐 때(밤 · 이른 아침). 팀장에게 5분 미리 알린다.
- [ ] SQL Editor 의 실행 역할은 **기본(postgres)**. '사용자로 실행(역할 바꾸기)' 은 끈다 — 로그인한 사용자로 실행하면 0023 장치가 SQL Editor 작업도 막는다.

## 2. 백업 — 자료는 바뀌지 않지만 보험으로

0023 · 0024 는 자료를 넣거나 고치거나 지우지 않는다(장치 · 함수 · 칸 하나). 그래도 아래 셋을 먼저 한다.

1. **자동 백업 확인** — Supabase 대시보드 › Database › Backups 에서 오늘(또는 어제) 백업이 보이는지, 시점 복구(PITR)가 켜졌는지 본다.
   요금제마다 다르다(무료 요금제는 내려받기 · 복구 화면이 없을 수 있다) — **운영 프로젝트의 설정은 확인하지 못했다.**
2. **앱 백업** — 대표 화면 › 설정 › 작업공간 › [백업 내려받기] 를 대표 작업공간 · 팀장 작업공간(팀장 화면으로 바꿔서) 각각 한 번.
   업체 · 업무 일기 · 모듈 기록 · 서류 파일 목록이 담긴다(서류 원본 파일은 빠진다 — 화면에 보장 범위가 적혀 있다).
3. **바꾸는 함수 본문** — precheck 7 · 8번이 '0020 그대로' 면 따로 할 일 없음: `rollback_0023_0024.sql` 이 같은 본문을 담고 있다(로컬에서 되돌린 본문의 지문이 0020 과 같음을 확인).
   '다름' 이면 아래 둘의 결과를 복사해 보관한다(읽기만):
   ```sql
   select pg_get_functiondef('public.os_access_link_owner_to_pilots()'::regprocedure);
   select pg_get_functiondef('public.my_pilot_views()'::regprocedure);
   ```

(선택) 개발자 PC 에서 `supabase db dump` 로 구조를 받아 둘 수 있다 — DB 비밀번호는 저장소 · 채팅 · 문서에 붙이지 않는다.

## 3. 실행 순서 — 파일을 **통째로** 붙여 넣고 실행

SQL Editor 는 붙여 넣은 글을 한 덩어리(한 거래)로 보내고 **마지막 결과 하나만** 보여 준다. 그래서 점검 파일은 모두 표 하나로 끝나게 만들었다.

| 단계 | 파일 | 기대 결과 | 다르면 |
|---|---|---|---|
| ① | `supabase/manual/check_applied_0016_0024.sql` | 맨 첫 줄 '읽기 전용 거래 = on' · 0016~0022 들어감 · 0023 · 0024 없음 | §1 첫 칸 |
| ② | `supabase/manual/precheck_0023_0024.sql` | 멈춤 0 · 11번 숫자 적기 | 멈춤 줄의 안내대로 · 시작하지 않는다 |
| ③ | 맨 앞에 `set lock_timeout = '5s';` 한 줄 + `supabase/migrations/20261104000023_workspace_id_lock.sql` | 마지막 표 = 장치가 붙은 표 이름(precheck 6번 수만큼 · 로컬 19). 'trigger … does not exist, skipping' 알림은 정상 | 'lock timeout' → **아무것도 바뀌지 않았다**(한 거래). 몇 분 뒤 다시 |
| ④ | 맨 앞에 `set lock_timeout = '5s';` 한 줄 + `supabase/migrations/20261104000024_customer_audience.sql` | 마지막 표 = `full · internal · n` / `pilot · internal · m` (customer 줄 없음) | '0019 · 0020 을 먼저' → 아무것도 안 바뀜 · ① 다시 |
| ⑤ | `supabase/manual/verify_after_0023_0024.sql` | 12줄 모두 **좋음** · 7번 'n / n' 이 ② 11번과 같음 | §5 되돌리기 검토 · 화면 보내기 |
| ⑥ | `supabase/manual/try_0023_0024.sql` | **빨간 오류 글처럼** 나오는 것이 정상: `[점검 끝 · 정상] 통과 4 · 실패 0` + ✓ 네 줄(옮기기 막힘 · 같은 곳 저장 됨 · 팀장→고객 막힘 · 팀장 화면 그대로) | ✗ 줄 → §5 |

| ⑧ | ① 다시 | 0023 · 0024 **들어감** | — |

⑥ 은 대표 업체 하나 · 팀장 계정 하나로 '대표로서' 고치기를 시도해 보고 **마지막에 일부러 오류를 내어 전부 되돌린다**(로컬에서 업체 고친 시각 · 작업공간 · 계정 대상이 그대로임을 확인). 결과 글에는 수와 ✓/✗ 만 — 이름 · 이메일 · 업체 이름은 나오지 않는다.

적용이 끝나면 ⑤ ⑥ ⑧ 결과 화면을 보내 준다 → 개발 쪽이 `docs/PRODUCT_MASTER_PLAN.md` 진행판(SAFE-2 · SEC-4 · SEC-5)을 '운영 적용 완료' 로 고친다.

## 4. 충돌 위험 · 대응

1. **잠금** — ③ 은 19개 표에 장치를 붙이며 표마다 짧게(밀리초) 쓰기를 멈추게 하고, ④ 는 계정 표(os_access)에 칸 하나를 더하며 잠깐 잠근다.
   오래 열린 거래가 있으면 기다리게 되는데, `lock_timeout 5초` 를 붙였으므로 기다리지 않고 실패한다 → 파일 전체가 한 거래라 **반쯤 적용된 상태는 없다**. precheck 17번(오래 걸린 거래)이 0 일 때 하면 거의 없다.
2. **함수 덮어쓰기** — ④ 는 `os_access_link_owner_to_pilots` · `my_pilot_views` 를 다시 만든다. 운영에서 누가 고쳤다면 그 고침이 사라진다 → precheck 7 · 8번 지문으로 먼저 확인(로컬 0020 본문 지문 `5923bce0…` · `b9e5de27…`).
3. **이름 겹침** — 새 함수 넷 · 트리거 넷의 이름이 이미 있으면 precheck 9번이 알린다. 전에 0023 · 0024 를 실행했다면 정상(다시 실행해도 같다).
4. **이미 섞인 기록** — 0023 은 **앞으로** 옮겨지는 것을 막을 뿐, 이미 옮겨진 줄을 되돌리지 않는다. precheck 15(예전 id 기록) · 16(마케팅 기록)이 0 이 아니면
   적용과 별개로, 대표 확인 뒤 SQL Editor 에서 정리한다(SQL Editor 는 0023 장치가 막지 않는다).
5. **앱의 '고정 id' 저장 두 곳 — D-538 에서 고침(앱만 · DB 변경 0)** — AI 자체점검 기준(`self-check` · 특허 · 벤처 AI 판) · 스레드 '이번 주 참고'(`wk_<주>`)는
   id 가 작업공간과 상관없이 같아서, 대표가 **팀장 화면에서** 저장하면 대표 줄이 팀장 작업공간으로 옮겨졌고(0023 전) · 0023 뒤에는 그 저장이 막혔다.
   팀장 본인은 대표가 먼저 만든 같은 id 줄 때문에 처음부터 저장이 안 됐다.
   - 지금(D-538 뒤): 새 저장은 `self-check_<작업공간>` · `wk_<주>_<작업공간>` — 작업공간마다 따로라 옮겨짐 · 막힘이 없다. 예전 줄은 지우지 않고, 새 줄이 없으면 이어서 읽는다.
   - 시험: `qa:modconflict` F1~F6(진짜 PostgREST · 0023 장치) — 고치기 전 재현(옮겨짐 · 막힘 · 팀장 본인 저장 안 됨) → 고친 뒤 두 작업공간 · 팀장 본인 모두 저장.
   - 기업마당 공고(`biz_<번호>`)는 처음 보고에 넣었으나 **저장하는 길이 없다**(읽기 전용 — 고치기 · 공개 · 지우기 단추가 숨겨짐 · 직접 넣은 공고는 무작위 id). 고칠 것 없음(D-538 정정).
6. **앱의 다른 저장 길** — 코드 조사: `workspace_id` 를 다른 값으로 바꾸는 앱 코드 · DB 함수는 없다(`set workspace_id =` 0건 · 앱 upsert 는 지금 작업공간 값). 백업 불러오기는 D-530 에서 다른 작업공간 업체를 건너뛰게 고쳤다.
7. **서버 작업** — SQL Editor · 서버(로그인한 사람이 없는 작업)는 막지 않는다. 대표가 직접 옮겨야 할 때는 SQL Editor 로.

## 5. 되돌리기 — 대표가 '되돌려' 라고 할 때만

`supabase/manual/rollback_0023_0024.sql` — 이번에 **더한 장치만** 뗀다(트리거 떼기 · 함수 두 개를 0020 본문으로). 표 · 칸 · 자료 · 정책은 그대로, audience 칸도 남긴다(칸 지우기 금지 · 기본값 internal 이라 무해).

- **외부 고객 계정이 하나라도 있으면 거부**한다 — 되돌리면 다음 팀장 준비 때 대표가 그 고객 작업공간 편집자로 들어갈 수 있어서다(고객 자료 보호가 먼저).
- 한 거래 — 중간에 실패하면 아무것도 바뀌지 않는다. 마지막 표 `0023 장치 0 · 0024 장치 0`.
- 되돌린 뒤 ① 에서 0023 · 0024 가 '없음', ② 7 · 8번이 '0020 그대로' 인지 본다(로컬 연습 통과).
- 다시 적용은 §3 ③ 부터 그대로(여러 번 실행해도 같다 — 로컬 연습 통과).

## 6. 대표 ↔ 내부 팀장 유지 · 외부 고객 분리 — 무엇이 보장되나

| 계정 | 만드는 방법 | 대표가 그 작업공간을 보나 | 팀장 화면 목록 | AI | 지키는 장치 |
|---|---|---|---|---|---|
| 대표 쪽(full) | 기존 | — | 내부 팀장 목록을 본다 | 대표 AI 작업실 · AI 도우미 | — |
| 내부 팀장(pilot · internal) | `pilot_provision.sql` | **본다**(편집자 자동 연결 — 0020 그대로) | 뜬다 | Gemini 만(서버가 막음) · 한도 없음(internal) | 0024 뒤에도 그대로(⑤ 7번 · ⑥ ④) |
| 외부 유료 고객(pilot · customer) | **`customer_provision.sql` 만**(0024 뒤) | **못 본다** — 자동 연결 0 · 대표 쪽 계정은 구성원이 될 수 없음(초대 · SQL Editor 모두 DB 가 막음) | 안 뜬다 | customer 요금제 · 월 한도 · 기한 | 0024 트리거 셋 · 연결 함수 조건 |

- 내부 팀장을 고객으로 바꾸려 하면(대표가 그 작업공간 구성원일 때) DB 가 멈춘다 — 자동으로 지우지 않는다(⑥ ③).
- 고객끼리 · 고객 ↔ 대표 자료는 작업공간 RLS 로 갈린다 — 같은 등급(pilot)의 격리 시험(`qa:isolation` 진짜 RLS · 모든 표 API 공격 · 무작위 80걸음 · `qa:pilot`)이 그대로 적용된다.
- 고객 플랫폼(portal)은 이와 별개 — `portal_*` 표와 고객 안전 함수만 읽는다(그대로).
- 고객 계정이 실제로 보는 메뉴(네 영역 — 마케팅 · 고객사 · 서류 · 일정 · 업무)는 D-562 ~ D-564 에서 만들었다(전문 모듈 · 영업자 정산 · 1차 미팅 체크리스트는 닫힘). 고객 계정을 여는 순서는 아래 §9.
- 참고: 직원용 고객 찾기 함수(`staff_find_customer_profile`)는 대표 쪽(full) 계정만 부를 수 있다 — 외부 고객은 못 부른다(0019).

## 8. 0025 — 고객 문의 · 화면 오류(D-568) · 0024 다음에

- 무엇: 표 하나(`support_messages`) · 정책 하나 · 함수 여섯. **기존 표 · 열 · 정책 · 자료는 건드리지 않는다.** 선행은 0019(0024 가 없어도 돈다).
- 왜 지금: 외부 고객 계정을 열면(0024 뒤) 고객 화면의 오류 · 문의가 대표에게 닿을 길이 이것뿐이다. 없으면 앱은 문의 단추를 숨기고 예전처럼 돈다.
- (D-599) 운영 profiles 모양(display_name 없음)에서 멈추던 것을 고쳤다 — 2026-11-11 이전에 받은 0025 파일로 실패했다면 지금 파일로 다시 실행한다(그때 바뀐 것은 없다).
- (D-600) **운영 적용 완료 2026-11-12** — 고친 파일로 다시 실행 → 확인 결과 '들어감'.
- 실행: `supabase/migrations/20261110000025_support_messages.sql` 을 **통째로** 붙여 실행 → 마지막 결과 한 줄이
  `table_count 1 · policy_count 1 · function_count 6 · authenticated_grants SELECT` 이면 끝. 여러 번 실행해도 같다.
- 확인: `supabase/manual/check_applied_0016_0024.sql` 의 25번 줄이 '들어감'. 대표 계정으로 로그인 → 설정 › 받은 피드백함에 탭 [문의 · 오류] 가 보인다.
- 되돌리기(필요할 때만): 함수 여섯 개의 실행 권한을 거두면 앱은 단추를 숨긴다 — 표는 남겨도 무해(지우지 않는다).
- 로컬 시험: `npm run qa:db`(test-0025-support.sql 51줄) · `npm run qa:pilot`(고객 → 대표 받은함 → 답장 → 고객 화면 · 고객/팀장 토큰 공격).

## 9. AI 사용량 비밀값 넣은 뒤 — 팀장 마케팅 AI 권한(D-600)

- 0022 를 처음 넣을 때 그때 있던 팀장(pilot) 계정에 `ai_entitlements` 줄이 **마케팅 꺼짐**(`marketing = false`)으로 만들어진다.
  비밀값(`ai_usage_config`)이 없는 동안에는 이 값을 보지 않지만, 비밀값을 넣으면 서버가 이 값을 보고 **팀장 마케팅 AI 단추를 닫는다.**
- 그래서 비밀값을 넣은 뒤 한 번 확인한다(읽기만): `select kind, marketing from public.ai_entitlements;` → internal 이 false 이면
  `update public.ai_entitlements set marketing = true, updated_at = now() where kind = 'internal' returning kind, marketing;`(D-564 — 팀장에게도 마케팅 AI).
  `supabase/manual/pilot_provision.sql` 로 새로 연 팀장 계정은 처음부터 켜짐이다.
- 운영(2026-11-12): 비밀값 들어감(09:58) · internal 이 꺼짐이었음 → 대표가 위 update 실행 → true.
- Vercel `AI_USAGE_SECRET` 이 DB 의 해시와 맞는지는 SQL 로 볼 수 없다 — 팀장 계정으로 마케팅 AI 단추를 한 번 눌러 글이 나오면 맞다.
  '이 AI 기능은 사용량 관리가 준비되면 열립니다' 가 뜨면 값이 다르다(Production 체크 · 앞뒤 빈칸 · 값을 넣은 뒤 Redeploy).

## 9. 첫 고객 계정 여는 순서 (0022 ~ 0024 적용 뒤 · 대표가 실행)

1. 고객이 `https://os.miraeailab.com` 에서 **직접 가입**한다(이름 · 이메일 · 비밀번호). 가입 화면에 '담당자가 승인하면 바로 쓸 수 있어요' 라고 미리 알려 준다.
2. 고객 화면에 **'이 계정은 아직 사용 승인 전이에요'** 가 뜬다(D-579) — 화면의 이메일을 [복사] 해서 대표에게 보낸다.
   (대표가 계정을 만들어 줄 때는 1 · 2 대신 Authentication → Users → Add user · 'Auto Confirm User' 체크.)
3. 대표가 SQL Editor 에서 `supabase/manual/customer_provision.sql` 을 연다 — 맨 위 여섯 줄(이메일 · 작업공간 이름 · 요금제 · 월 AI 한도 · 기한 · 마케팅 AI)만 바꿔 실행한다.
   아래 확인 줄에 그 고객이 **owner 한 사람 · 업체 0** 으로 나오면 된 것이다(대표는 구성원이 아니다).
4. 고객은 그 화면에서 **[승인됐는지 다시 확인]** 만 누른다 — 첫 화면 '환영합니다 — 어디서 시작할까요?' 가 열린다.
5. 고객에게 `docs/PILOT_CUSTOMER_GUIDE.md` 를 채워 보낸다(가격 · 해지 · 연락처는 대표가 정한 값으로).

- 0025(문의하기)를 아직 적용하지 않았으면 고객 화면에 [문의하기] 단추가 없다 — 그동안은 안내 한 장의 연락처로 받는다.
